# Problem statement v0 — 视频剪辑（研究前的初稿）

证据等级：**requester + assumption** · 日期：2026-10-28 · 版本 0（Empathize 之前写的；预设了问题本身，Define 阶段会按证据重写）

> 这一版的用途是推导研究主题和访谈指南的主题，不作为设计依据。凡是没有来源的句子都是假设，标 [A]。

## Who
主要用户：一个人包揽拍、剪、发的视频创作者。他们同时做几种形态：口播/知识类、游戏实况、直播切片、混剪、鬼畜。[A：多形态并存来自需求方 R2/R3，具体人群待 traces 验证]
其他受影响者：
- **观众**：决定完播和互动，也就是需求方说的"爆款"（R5）
- **被切片的主播 / 被鬼畜的人 / 音乐版权方**：权利人
- **接手精剪的剪辑师**：接收粗剪工程
- **代用户操作的 AI agent 和为 token 付费的人**：见 ACI 侧文档

## What
- 现状 [A]：从原始素材到可发布成片，大量时间花在机械性判断上：哪里没人说话、哪里说错重来、哪一段是高光、画面该在哪一拍切。现有自动工具（剪映智能剪口播、auto-editor、Descript、Opus Clip）要么只覆盖其中一种形态，要么剪得生硬、需要大量返工，要么做出来的视频"不像能火的"。
- 期望状态：创作者把注意力放在内容和创意决定上；机械性判断有可靠的初稿，可以快速审阅和修正；成片在开头、节奏、字幕、画幅等方面达到平台上表现好的视频的水准。
- 未满足的需求 [A]：一个能信任、能快速核对、能覆盖他们实际在做的各种形态的"初稿"。

## When / Where
[A] 录完素材后的当天或第二天，在自己电脑上；直播结束后要赶在热度消退之前出切片（时效性）；投稿前的最后检查。

## Why it matters
[A] 剪辑耗时常是素材时长的数倍；切片的时效窗口短，晚发就没量；创作者因为剪辑负担而降低更新频率。需求方把成功定义为"爆款"（R5），也就是观众侧的结果。

## What we know / still need to learn
- 已知（来源）：需求方要覆盖的形态（R2、R3）；验收标准（R5）；参考了 Remotion 的路线（R4）。
- 未知 → 研究问题：
  1. 各形态的创作者现在的实际步骤是什么，在哪一步花时间、在哪一步出错？（traces、访谈）
  2. 他们怎么判断"这段该不该剪""这条剪得好不好"？什么情况下信任自动结果，什么情况下不信？
  3. 他们发布后怎么复盘？剪辑上哪些做法被认为和完播率、互动相关？
  4. 自动结果出来以后，他们在哪里修改：剪辑软件时间线、文字稿，还是重新渲染？
  5. 哪些形态里，"自动"本身会被社区排斥（例如鬼畜的手艺属性）？

## Backup problems
1. 只聚焦直播切片的时效性：长录像出高光短片的速度。
2. 只聚焦口播/知识类的"去废片"：停顿、重说、口头禅。
